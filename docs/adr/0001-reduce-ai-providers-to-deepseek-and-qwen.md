# 1. 将 AI 提供商缩减为仅保留 DeepSeek 和通义千问

- 状态：提议（机器推断）
- 日期：2026-08-21

## 上下文

应用原本支持 7 个 AI 提供商（DeepSeek、通义千问、OpenAI、Anthropic、OpenAI 兼容、Google AI、Ollama），但用户希望聚焦于中国大陆可用的中英翻译模型。根据调研，DeepSeek 和通义千问（Qwen）在翻译评测中表现优秀且 API 价格合理，其余提供商要么在大陆不可直接使用（如 OpenAI、Anthropic、Google AI），要么维护成本高且使用场景有限（如 OpenAI 兼容自定义端点、Ollama 本地模型）。代码库中存在大量与已删除提供商相关的分支逻辑、自定义端点/模型输入、迁移代码和测试，需要彻底清理以避免死代码和用户困惑。

## 决策

将 AIProvider 枚举从 7 个 case 缩减为仅保留 deepseek 和 qwen 两个 case。删除所有与已删除提供商相关的 switch 分支、needsCustomEndpoint/needsCustomModel 属性、自定义端点输入框、自由模型名输入框、模型迁移逻辑（migrateModelOverrides 及其辅助方法）以及对应的测试用例。保留 needsAPIKey 属性（恒为 true）和 Keychain 中已有的 DeepSeek/Qwen API Key 数据。同步更新官网文档中关于支持提供商的描述。

## 后果

正面：代码库大幅简化，移除约 5 个提供商相关的分支和死代码，降低维护成本；用户界面更简洁，不再需要处理自定义端点/模型等高级配置；测试更聚焦于实际支持的提供商；减少因 OpenAI 兼容/Google AI 等提供商 API 格式差异导致的解析错误风险。负面：失去对 OpenAI、Anthropic、Google AI 等模型的支持，用户无法再使用这些模型进行翻译；已删除提供商的残留 Keychain/UserDefaults 数据不会被清理（但也不再被读取，无实际影响）；如果未来需要重新支持这些提供商，需要重新实现相关代码。

## 被拒备选

保留全部 7 个提供商：用户明确要求只保留两个，且其余提供商在大陆不可用或使用率低，保留会增加维护负担。仅隐藏 UI 但保留代码：用户要求彻底删除，且保留死代码会误导后续维护者。保留 OpenAI 兼容自定义端点：该功能允许用户接入任意 OpenAI 兼容 API，但用户未要求保留，且会增加配置复杂度。保留 Ollama 本地模型：用户未要求保留，且本地模型翻译质量通常不如云端模型。清理已删除提供商的残留数据：用户确认不主动清理，避免过度设计，且残留数据无害。
