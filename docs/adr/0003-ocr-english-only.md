# 3. Windows 版 OCR 仅支持英文（不做中文兜底）

- 状态：已接受
- 日期：2026-10-02

## 上下文

macOS 版 OCR 使用 Apple Vision，**单次请求即可多语言**（`OCREngine.swift` 一次列出 `en-US, en-GB, zh-Hans, zh-Hant`）。
Windows 版使用 WinRT `Windows.Media.Ocr`，**每个引擎只支持一种语言**，且没有多语言引擎。因此移植时必须在语言覆盖上显式做出选择。产品定位为「英语精读翻译助手」，经确认：**截图 OCR 的源文本域为纯英文，不包含中文**。

## 决策

### 本质

产品范围界定问题（可逆、低风险）：截图 OCR 需要覆盖哪些语言。WinRT 的单语言限制只是把这个范围问题变成必须显式选择的技术约束。

### 最佳实践

对「单语言 OCR 引擎 + 混排文档」，业界常规做法是**多引擎 + 按脚本合并**；而「主引擎结果为空才回退」对混排会丢中文——实测 `sample_table.png`（中英词汇表）英文列被 en 引擎读到后结果非空，中文列全部为空。但若源域**确为纯英文**，只配 en 引擎是符合 YAGNI 的正当选择，不宜为未证实的场景预建重逻辑。

### 方案

Windows OCR 只配 `en-US` 引擎（缺包时引导用户安装），**不实现** zh-Hans 兜底或双引擎合并。若未来源域扩大到中英混排，再以「en + zh 双引擎、按 CJK 字符过滤后合并」补齐（Core 纯函数 `OcrMerge`，TDD 先行）。

## 后果

正面：实现简单，无额外 OCR 往返开销，与产品定位一致。
负面：截图若含中文，中文部分识别为空（已知限制）；mac 版仍保留多语言能力，两平台行为不完全一致（对纯英文源域无害）。

## 被拒备选

- **「en 结果为空则回退 zh」**：对中英混排失效（英文列已读到 → 不触发回退 → 中文仍丢失），已实测证伪。
- **「en + zh 双引擎合并」**：对纯英文源域属过度设计（2× OCR 开销 + 几何去重复杂度），暂不做，留作触发条件明确的后续项。
